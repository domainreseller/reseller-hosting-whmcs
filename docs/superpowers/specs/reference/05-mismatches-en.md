# 14 semantic mismatches between cPanel and Plesk (recon output)

1. OBJECT MODEL (the big one). 1 WHMCS service = 1 cPanel account, but = 2 Plesk objects (customer + webspace) where the CUSTOMER IS SHARED across all of that client's services. This single fact cascades into four separate decisions: (a) create must look up an existing customer before adding or it duplicates them; (b) terminate must cascade-delete the customer only when the last webspace goes; (c) change-password must not rewrite the shared panel password from a secondary subscription; (d) suspending one WHMCS service must not suspend the customer. Any abstraction that assumes 'one service == one panel user' will silently corrupt multi-service Plesk clients. Requires a persistent WHMCS-client -> Plesk-customer map (the bundled module uses mod_pleskaccounts keyed on userid+usertype).

2. PANEL TYPE HAS NO NATIVE PER-SERVER STORAGE IN WHMCS 7.8. Product config options are per-product and are absent from all server-params-only contexts (UsageUpdate, TestConnection, ListAccounts, GetUserCount, GetRemoteMetaData, AdminSingleSignOn, ConfigOptions Loader). Six entry points would have no way to choose a driver. Options are: a module-owned table keyed on serverid (works, needs seeding/probing and has no native admin UI), the port as a heuristic (fragile), encoding the type into the username/accesshash string (ugly but universal), or abandoning the single-module requirement in favour of two thin shim modules sharing one lib (cleanest, but contradicts the brief). This is a structural decision that must be made before any code is written.

3. serveraccesshash COLLISION. Verified directly: the cPanel module reads serveraccesshash as the API token (cpanel.php:687), while the Plesk module reads the same field as the PORT NUMBER in four places (Loader.php:14, plesk.php:43, V1000.php:85, V1635.php:24). A unified module must pick one meaning. Choosing 'token' means every existing Plesk server row whose accesshash currently holds '8443' needs a migration, and the value is stored PLAINTEXT in tblservers (unlike password, which is encrypted) — so anyone with DB read access already holds panel-root-equivalent credentials.

4. PLESK IS BROKEN ON 18.0.80+ AND THE ROOT CAUSE IS STRUCTURAL. I confirmed in-tree: _setWebspaceStatus and _setWebspacePassword are declared ONLY in Plesk_Manager_V1000, only 1.0.0.0 templates exist for them, and both are rooted at the <domain> operator that Plesk 18.0.80 now rejects (error 1014). Because Plesk_Manager_Base::__call pins the packet version to the DECLARING class, they are permanently forced to 1.0.0.0. Result: suspend, unsuspend and the FTP half of change-password are dead on current Plesk, while terminate (overridden in V1630, <webspace>-rooted) still works. Tracked as WHMCS-27532, Critical/Backlog, no ETA. The new module must emit <webspace><set>. This is the single strongest justification for the project.

5. SUSPENSION SEMANTICS. cPanel: a boolean flag plus a free-text reason. Plesk: a BITMASK (0 active, 16 suspended-by-admin, 32 suspended-by-reseller) with NO reason field, where a reseller generally cannot clear an admin-set suspension, and unsuspend is the same 'set status' verb with 0 — which wipes every bit including one a reseller shouldn't be able to clear. Decisions needed: where does WHMCS suspendreason go on Plesk (drop it, or write it to a description field)? How is the admin-vs-reseller bit chosen — the bundled module string-compares serverusername against 'root'/'admin', which breaks if a reseller happens to be named 'admin'. What should unsuspend do when it finds bit 16 set and holds only reseller credentials?

6. TWO PASSWORDS ON PLESK, ONE ON CPANEL. Plesk has a panel/customer login (addressed by numeric id) and a subscription system/FTP user (addressed by domain). WHMCS has a single 'password' service property. The bundled module fans out to both but silently no-ops the panel half when accountInfo.login != params.username, so a secondary subscription reports success while changing nothing. Needs an explicit policy, not a silent guard.

7. PACKAGE REFERENCE MODEL. cPanel takes a plain plan NAME but auto-prefixes reseller-created packages as '<reseller>_<Name>', so resolution must try both forms against listpkgs (a reseller may also hold access to root's unprefixed global packages). Plesk does not rewrite names but SCOPES visibility ('you can use only service plans to which the XML API requester has access'), and switching a plan requires a name->GUID round-trip that creation does not. Same admin-facing config field, two different resolution algorithms and two different failure modes. Two in-tree bugs not to copy: cpanel.php:169 prefixes the fallback with the NEW ACCOUNT's username instead of the reseller login, and cpanel.php:1333 de-prefixes with explode('_',$plan)[1], mangling any package name containing an underscore.

8. SSO SHAPES DO NOT LINE UP. cPanel create_user_session returns a complete ready-to-use URL that drops straight into WHMCS's ['success'=>true,'redirectTo'=>$url] contract. Plesk server.create_session returns a bare session id that must be POSTed to /enterprise/rsession_init.php — which is precisely why the bundled Plesk module implements NO SingleSignOn function at all (verified: zero grep hits) and renders a raw HTML form in ClientArea instead. Additionally cPanel mints sessions for an ACCOUNT while Plesk mints them for a LOGIN, and cPanel's session is issued to the WHMCS server's outbound IP but consumed by the customer's browser, which WHM's session-IP validation can reject. Decision: force Plesk into a redirectable URL (rsession_init.php GET with success_redirect_url, or REST POST /api/v2/server/session) to keep one code path, or accept two different client-area UX paths.

9. USAGE UNITS AND SENTINELS, THREE-WAY. cPanel listaccts returns disk as 'NNNM' strings (already MB); cPanel showbw returns BYTES; Plesk returns BYTES everywhere. No-limit sentinel is the literal string 'unlimited' on cPanel and -1 on Plesk. WHMCS tblhosting wants MB. The bundled cPanel module additionally does NO unit conversion at all on the resellerstats path while converting on the cPanel-account path, so reseller usage figures are already wrong/inconsistent today. Also note Plesk's V1630 divides disklimit and bwlimit uniformly, turning an 'unlimited' (-1) limit into a tiny negative number.

10. PLESK TRANSPORT CHOICE IS UNRESOLVED. REST v2 coverage is genuinely incomplete: /clients, /domains, /server, /server/session, /auth/keys and /cli/{utility}/call are confirmed real, but suspend/activate, plan switch, subscription password and plan listing have no confirmed native REST verb — the field workaround is POST /api/v2/cli/subscription/call, a shell-argument passthrough returning unstructured stdout rather than typed JSON. XML-API (with a KEY header, using <webspace> not <domain>) remains the only surface with typed responses for all nine WHMCS actions. Recon explicitly flagged that it could NOT retrieve the full Plesk openapi.yml, so the 'not confirmed' list is unverified and must be checked against a live 18.0.8x panel.

11. PLESK API KEYS ARE IP-BOUND IN A WAY WHM TOKENS ARE NOT. Creating a key via XML-API without an explicit <ip_address> binds it to the sender's IP; the secret_key CLI without -ip-address reportedly leaves it unbound. The two vendor docs disagree. A WHMCS box behind NAT, with multiple outbound IPs, or that gets migrated will silently start failing auth. Separately, Plesk reseller API access requires an 'Ability to use XML API' permission that is OFF by default and is independent of the key itself.

12. USAGEUPDATE RECEIVES SERVER PARAMS ONLY. Verified at modulefunctions.php:302-320 — it is called once per enabled server with getServerParams() and nothing else: no serviceid, no username, no domain, no configoptions. The module must query WHMCS itself to discover which services live on this server, bulk-fetch from the panel, and write back per row. It returns nothing; any non-empty return other than 'success' is logged as a failure. Both panels also need a per-service key to join on, and the natural key differs (cPanel: domain or username; Plesk: webspace name), which interacts with the AccountRef design.

13. RESELLER-ACCOUNT PRODUCT TYPE DIVERGES SHARPLY. On cPanel, a reseller product means setupreseller + setacls + setresellerlimits + setresellernameservers and a completely separate suspend/terminate/usage path. On Plesk it means reseller.add with a reseller plan, and the bundled module returns 'success' immediately without ever creating a webspace. cPanel exposes 10 reseller-specific config options (15-24); Plesk exposes one. Whether reselleraccount is in scope at all is a scoping decision with large surface-area consequences.

14. CONFIG OPTION SURFACE IS ASYMMETRIC AND POSITIONALLY FROZEN. cPanel ships 24 options; Plesk ships 4. configoptionN binds by ORDINAL POSITION (verified: while ($counter <= 24)), so once released, inserting or reordering an entry silently re-maps every stored product value. A unified option set must be designed once, append-only forever, and must degrade sanely when a field is meaningless for the active panel (e.g. Plesk's IP-mode dropdown is silently ignored unless the API login is literally 'admin').
